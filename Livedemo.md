# How the `livedemo` Process Works

> How the PsycedelicAI live-demonstration workflow is activated, reconstructed
> and applied when Psycedelic loads the keyword `livedemo`.

---

## Overview

`livedemo` is a codeword for activating a combined PsycedelicAI working method.

It refers to a process for:

- recovering relevant project context;
- searching previous conversations;
- reconstructing the current working method;
- loading the appropriate public source areas;
- preserving human intent and authority;
- adapting the method to the current task;
- creating a structured and reviewable result.

The keyword does not cause an AI system to magically remember everything.

It activates a method when the necessary context is already available or can be
retrieved.

The method is designed to demonstrate whether meaningful project continuity can
be reconstructed and used in a new working situation.

---

# What `livedemo` Means

The shortest definition is:

> **`livedemo` activates a context-recovery and document-generation workflow based on the accumulated PsycedelicAI method.**

A more complete definition is:

> **`livedemo` is a keyword that instructs the AI to search for the previous method and relevant context, reconstruct the current activation protocol, connect the appropriate PsycedelicAI sources, adapt the method to the current task and produce a structured result for human review.**

The process is not:

```text
Keyword
    ↓
Generate random output
```

It is:

```text
Keyword
    ↓
Search
    ↓
Find
    ↓
Filter
    ↓
Reconstruct
    ↓
Connect
    ↓
Adapt
    ↓
Create
    ↓
Review
```

# What Happens When `livedemo` Is Loaded?

## 1. The keyword is recognised

When Psycedelic writes:

```text
livedemo
```

the AI interprets it as a request to activate the PsycedelicAI
live-demonstration workflow.

The keyword is a compact reference to a larger set of previously defined
instructions, source areas, concepts and working rules.

The keyword itself is not the complete context.

It is an activation point for retrieving and applying that context.

---

## 2. Previous `livedemo` conversations are searched

The AI searches previous conversations for references to:

- the original definition of `livedemo`;
- later updates to the protocol;
- instructions about invoked repositories;
- rules for searching older chats;
- filename-generation requirements;
- output and formatting requirements;
- limitations and authority rules;
- previous demonstrations and tests;
- related supporting concepts.

The search should not only find the literal word.

It should also recover the development of the method around the word.

The goal is to determine:

> What does `livedemo` mean now, after all later changes and additions?

---

## 3. Direct and supporting material are separated

Not every conversation that mentions `livedemo` has the same importance.

### Direct source material

Direct sources may include conversations where Psycedelic:

- defined the keyword;
- changed its behaviour;
- added a new protocol rule;
- requested a list of invoked files;
- tested the keyword in a new chat;
- specified how old-chat searches should be reported;
- required a suggested Markdown filename;
- explained what the activation should demonstrate.

### Supporting source material

Supporting sources may include conversations about:

- AI Continuity;
- Portable Workstates;
- Memory Banks;
- Freeze States;
- Intent and Authority;
- Session Handoff;
- Trust Architecture;
- verification;
- recovery;
- Project Aurora;
- Fable Metadata;
- Symbiosis;
- human-AI collaboration.

Supporting material helps explain the working method, but it is not
automatically part of the direct activation record.

---

## 4. The search result is reported compactly

Psycedelic previously defined that an older-chat search should not flood the
conversation with a complete historical report.

The AI should instead provide a compact confirmation, such as:

> I found relevant older chats about `livedemo`, its activation rules, source
> repositories and related project material.

The older conversations are then used as working context for the current task.

This keeps the process useful without filling the visible conversation with
unnecessary historical material.

---

## 5. The current protocol is reconstructed

The AI compares the retrieved material and reconstructs the latest applicable
version of the method.

This includes identifying:

- which instructions are still active;
- which rules were added later;
- whether any older instructions were replaced;
- which source repositories should be considered;
- what limitations apply;
- what the current task requires;
- what type of output should be generated.

The AI should not simply copy the oldest definition of `livedemo`.

It should attempt to reconstruct the current working state of the protocol.

# The `livedemo` Working Process

After the relevant context has been recovered, the AI applies the following
process.

```text
1. Identify the current task
        ↓
2. Identify the intended output
        ↓
3. Recover relevant project context
        ↓
4. Select the relevant source areas
        ↓
5. Preserve human intent and authority
        ↓
6. Identify constraints and trust boundaries
        ↓
7. Separate facts, interpretations and assumptions
        ↓
8. Apply the relevant working method
        ↓
9. Suggest a filename if a Markdown document is being created
        ↓
10. Generate an output adapted to the task
        ↓
11. Review limitations, uncertainty and provenance
        ↓
12. Return the result for human review
```

The process should remain proportional to the task.

A short public comment does not need to display the full architecture.

A technical protocol may need:

- scope;
- authority;
- verification;
- stop conditions;
- recovery;
- auditability.

A project map should focus on:

- relationships;
- repository roles;
- navigation;
- status;
- limitations.

# Task Adaptation

The `livedemo` method is not intended to force one format onto every problem.

## LinkedIn Comment

The output should be:

- short;
- natural;
- readable;
- appropriate to the user's tone;
- connected to the relevant idea;
- linked to the most relevant source only.

## Email

The output should be:

- clear;
- professional;
- direct;
- appropriate for the recipient;
- limited to relevant background;
- reviewed before sending.

## Markdown Documentation

The output should include:

- a clear filename;
- a useful title;
- a defined purpose;
- appropriate sections;
- limitations;
- relationships to other material;
- a status where relevant.

## Security Protocol

The output may need to include:

- identity;
- authority;
- trust boundaries;
- capability scope;
- verification;
- approval gates;
- stop conditions;
- audit;
- recovery.

## Project Map

The output should focus on:

- project relationships;
- repository roles;
- navigation;
- current status;
- implementation distinctions.

The underlying method remains consistent while the visible structure changes.

# Markdown Generation Rules

When `livedemo` is used to create a new Markdown document, the AI should first
suggest a filename.

Example:

```text
wiki/Live-Demonstration-Method.md
```

The filename should communicate:

- the document's purpose;
- its intended location;
- its relationship to the project;
- whether it is a guide, protocol, map, glossary or status document.

The document should not be a random summary of previous conversations.

It should be a reusable and reviewable document that records the relevant
working method.

The generated Markdown should distinguish between:

- facts;
- interpretations;
- proposals;
- decisions;
- assumptions;
- uncertainty;
- permissions;
- technical limitations.

AI may:

Psycedelic remains responsible for:

- purpose;
- values;

- final decisions;
- publication;
- external commitments;
- acceptance of the result.

The output is not considered final merely because the AI generated it.

The human may:

- approve it;
- edit it;
- reject it;
- request a different interpretation;
- ask for additional validation;
- keep it private;
- publish it.

# What `livedemo` Does Not Do

The `livedemo` codeword does not:

- grant access to private repositories;
- create permanent memory;
- guarantee that every relevant conversation will be found;
- prove that all projects are technically integrated;
- make an AI system identical to a previous AI system;
- transfer human consciousness or lived experience;
- give AI permission to publish or act independently;
- turn an interpretation into a fact;
- turn a concept into an implementation;
- guarantee that a retrieved source is complete or current;
- remove the need for human review;
- replace technical or external validation.

It activates a working method when the necessary context is available or can be
retrieved.

---

# Portability and Activation Requirements

The `livedemo` keyword is not self-contained.

It is a compact reference to a larger working method.

Writing the word `livedemo` in another AI system will not, by itself, recreate
the full workflow.

For the method to work reliably, the receiving environment must have access to
the relevant activation components.

These may include:

- the `livedemo` keyword;
- the activation protocol;
- the current method definition;
- relevant project documentation;
- source repository links;
- previous conversation context;
- a Portable Workstate or continuity package;
- tools for searching and retrieving the required material;
- an AI system capable of following the process;
- human instructions, authority and review.

Without the required components, the receiving AI may:

- recognise the word but not know what it means;
- produce a generic interpretation of “live demo”;
- miss later protocol updates;
- fail to find the relevant source material;
- use the wrong project context;
- generate an unrelated document;
- apply the method incompletely;
- incorrectly assume that it has access to private or historical material.

In that situation, the keyword itself is not enough.

```text
Keyword
    without context
        = a label

Keyword
    with the activation protocol
        = a method reference

Keyword
    with the protocol, sources and working state
        = a potentially portable workflow
```

The method may therefore work reliably in one environment and fail or behave
differently in another.

This is not necessarily a failure of the concept.

It is evidence that the method depends on a continuity package rather than on the
keyword alone.

---

# Minimum Activation Package

A minimal portable activation package should include:

1. The definition of `livedemo`.
2. The current activation protocol.
3. The required source repositories and documentation areas.
4. The rules for searching previous conversations.
5. The output and filename requirements.
6. The distinction between facts, interpretations, assumptions, proposals and
   uncertainty.
7. Human authority and approval rules.
8. Known limitations.
9. Relevant current project context.
10. Instructions for reporting unavailable or inaccessible material.

A receiving AI should not claim that the full `livedemo` method is active until
it has enough information to apply these components.

# Activation Confidence

The receiving environment may report the activation state explicitly.

```text
Activation status: Partial
```

The keyword is known, but important context is missing.

```text
Activation status: Reconstructed
```

The activation protocol and relevant source material have been recovered.

```text
Activation status: Full working context available
```

The method, sources, current state and task requirements are available for the
current demonstration.

These statuses describe available working context.

They do not describe AI consciousness, identity or permanent memory.

# What the Process Demonstrates

A successful `livedemo` does not prove permanent memory.

It demonstrates a more specific capability:

```text
Previous method
    ↓
Relevant source retrieval
    ↓
Context reconstruction
    ↓
Project connection
    ↓
Task adaptation
    ↓
Structured output
    ↓
Human review
```

The demonstration is strongest when the task is new or not fully prewritten.

The important result is not only the final document.

It is the ability to:

- recover a working method;
- identify the relevant context;
- preserve intent;
- avoid unrelated material;
- create a useful result;
- show uncertainty;
- keep human authority visible.

# Portable Working Method

The `livedemo` workflow is intended to make the working method more portable
between:

- conversations;
- AI systems;
- models;
- platforms;
- projects;
- documents;
- future collaborators.

A codeword alone is not enough to transfer the complete method.

A reliable transfer also requires enough supporting context, such as:

- definitions;
- source links;
- project identity;
- working rules;
- current state;
- authority boundaries;
- relevant examples;
- limitations.

This reflects an important principle:

> A codeword can activate a method, but a portable continuity package must carry
> the method's context.

---

# Core Principles

The `livedemo` workflow is based on the following principles:

```text
Human intent comes before output.

Relevant context should be recovered before interpretation.

The newest applicable instruction should take priority over obsolete instructions.

Direct sources should be distinguished from supporting material.

Connected projects should not automatically be treated as one system.

Capability is not authority.

Memory is not continuity.

Access is not trust.

Context is not permission.

An interpretation is not automatically a fact.

A generated output is not automatically validated.

The visible output should match the task.

Human review remains the final approval point.
```
